# Module: Resource Management

| ID | User story | API | Acceptance criteria | Status |
|---|---|---|---|---|
| **US-001** | **As an administrator, I want to create a bookable resource, so that users can reserve it.** | `POST /api/resources` | • A resource contains a name, optional description, type, and optional location.<br>• Name is required, cannot be blank, and has a maximum length of 100 characters.<br>• Description has a maximum length of 500 characters.<br>• Location has a maximum length of 100 characters.<br>• Type is required and must be `ROOM`, `LAPTOP`, `CAMERA`, or `CAR`.<br>• New resources are active by default.<br>• The ID and timestamps are generated by the system.<br>• A valid request saves the resource and returns `201 Created`.<br>• Invalid input returns `400 Bad Request` and is not saved. | In progress |
| **US-002** | **As a user, I want to browse resources, so that I can find something suitable to book.** | `GET /api/resources` | • Only active resources are returned by default.<br>• Results can be filtered by type and location.<br>• Resources can be searched by name, case-insensitively.<br>• Multiple filters can be combined.<br>• Results are paginated.<br>• The default page size is 20 and the maximum is 100.<br>• Results can be sorted by name or location.<br>• An empty result returns an empty list.<br>• Invalid filter, page, or sorting values return `400 Bad Request`. | Todo |
| **US-003** | **As a user, I want to view a resource's details, so that I can decide whether it is suitable.** | `GET /api/resources/{id}` | • An existing resource returns `200 OK`.<br>• The response contains its ID, name, description, type, location, active status, and timestamps.<br>• A nonexistent resource returns `404 Not Found`.<br>• A malformed resource ID returns `400 Bad Request`.<br>• An inactive resource can still be retrieved directly by ID. | Todo |
| **US-004** | **As an administrator, I want to update a resource, so that its information remains accurate.** | `PUT /api/resources/{id}` | • Name, description, type, and location can be updated.<br>• The validation rules from resource creation still apply.<br>• The ID, active status, and creation timestamp cannot be changed through this request.<br>• The update timestamp changes after a successful update.<br>• A successful update returns `200 OK` with the updated resource.<br>• A nonexistent resource returns `404 Not Found`.<br>• Invalid input returns `400 Bad Request` and does not update the resource. | Todo |
| **US-005** | **As an administrator, I want to deactivate or reactivate a resource, so that unavailable resources remain stored without being bookable.** | `PATCH /api/resources/{id}/status` | • The request accepts an active status.<br>• A successful change returns `200 OK` with the updated resource.<br>• Deactivated resources remain in the database.<br>• Deactivated resources do not appear in the default resource list.<br>• Reactivated resources appear in the default resource list.<br>• Repeating the same status change succeeds without an additional side effect.<br>• A nonexistent resource returns `404 Not Found`.<br>• Missing or invalid input returns `400 Bad Request`. | Todo |

# Module: User Accounts

| ID | User story | API | Acceptance criteria | Status |
|---|---|---|---|---|
| **US-006** | **As a visitor, I want to create an account, so that I can book resources.** | `POST /api/auth/register` | • The request accepts a name, email address, and password.<br>• Name, email, and password are required.<br>• The email address must have a valid format.<br>• Email addresses are unique and compared case-insensitively.<br>• The password must contain at least 10 characters.<br>• Passwords are never stored as plain text.<br>• New accounts receive the `USER` role.<br>• Successful registration returns `201 Created`.<br>• A duplicate email returns `409 Conflict`.<br>• Invalid input returns `400 Bad Request`.<br>• Passwords and password hashes are never returned by the API. | Todo |

# Module: Authentication and Authorization

| ID | User story | API | Acceptance criteria | Status |
|---|---|---|---|---|
| **US-007** | **As a registered user, I want to log in, so that I can access protected features.** | `POST /api/auth/login` | • The request accepts an email address and password.<br>• Valid credentials authenticate the user.<br>• Invalid credentials return `401 Unauthorized`.<br>• The response supplies the authentication information required for later requests.<br>• Passwords and password hashes are never returned.<br>• Protected endpoints return `401 Unauthorized` when authentication is missing or invalid.<br>• The selected authentication approach is documented. | Todo |
| **US-008** | **As an administrator, I want resource-management operations to be restricted, so that regular users cannot modify resources.** | Existing resource endpoints | • Creating, updating, and changing the status of resources requires the `ADMIN` role.<br>• Authenticated users can list resources and view resource details.<br>• An unauthenticated request to a protected endpoint returns `401 Unauthorized`.<br>• An authenticated user without the required role receives `403 Forbidden`.<br>• Existing resource behavior remains unchanged for authorized users. | Todo |

### Technical decision for US-007

Before implementing authentication, choose and document one approach:

- Session and cookie authentication
- Token-based authentication

# Module: Resource Availability

| ID | User story | API | Acceptance criteria | Status |
|---|---|---|---|---|
| **US-009** | **As a user, I want to check whether a resource is available during a period, so that I know whether I can book it.** | `GET /api/resources/{id}/availability` | • The request accepts a start and end timestamp.<br>• Both timestamps are required.<br>• The start must be before the end.<br>• The start cannot be in the past.<br>• The result indicates whether the resource is available for the complete period.<br>• An inactive resource is unavailable.<br>• An existing active booking makes an overlapping period unavailable.<br>• A nonexistent resource returns `404 Not Found`.<br>• Invalid timestamps return `400 Bad Request`. | Todo |

### Period overlap rule

Two periods overlap when:

```text
existingStart < requestedEnd
AND
existingEnd > requestedStart
```

Periods that only touch at their endpoints do not overlap.

For example, a booking ending at `12:00` does not conflict with another booking starting at `12:00`.

# Module: Booking Management

| ID | User story | API | Acceptance criteria | Status |
|---|---|---|---|---|
| **US-010** | **As an authenticated user, I want to reserve an available resource, so that I can use it during a selected period.** | `POST /api/bookings` | • The request accepts a resource ID, start timestamp, end timestamp, and optional purpose.<br>• The start must be before the end.<br>• The start cannot be in the past.<br>• The purpose has a maximum length of 300 characters.<br>• The resource must exist and be active.<br>• The booking is associated with the authenticated user.<br>• A booking cannot overlap another active booking for the resource.<br>• A successful request saves the booking and returns `201 Created`.<br>• A nonexistent resource returns `404 Not Found`.<br>• An inactive or unavailable resource returns `409 Conflict`.<br>• Invalid input returns `400 Bad Request`. | Todo |
| **US-011** | **As an authenticated user, I want to view my bookings, so that I can manage my reservations.** | `GET /api/bookings/me` | • Only bookings belonging to the authenticated user are returned.<br>• Results include resource information, period, purpose, status, and creation time.<br>• Results can be filtered by booking status.<br>• Results can be filtered into upcoming and previous bookings.<br>• Results are paginated.<br>• Upcoming bookings are ordered by start time ascending.<br>• A user cannot retrieve another user's bookings through this endpoint.<br>• No matching bookings returns an empty result. | Todo |
| **US-012** | **As an authenticated user, I want to cancel my booking, so that the resource becomes available to others.** | `PATCH /api/bookings/{id}/cancel` | • A user can cancel their own active booking.<br>• An administrator can cancel any booking.<br>• A cancelled booking remains stored in the database.<br>• A cancelled booking no longer blocks resource availability.<br>• Cancelling an already cancelled booking succeeds without an additional side effect.<br>• A nonexistent booking returns `404 Not Found`.<br>• A user attempting to cancel another user's booking receives `403 Forbidden`. | Todo |

# Module: Resource Maintenance

| ID | User story | API | Acceptance criteria | Status |
|---|---|---|---|---|
| **US-013** | **As an administrator, I want to mark a resource unavailable for maintenance, so that users cannot book it during that period.** | `POST /api/resources/{id}/maintenance` | • The request accepts a start timestamp, end timestamp, and reason.<br>• Start, end, and reason are required.<br>• The start must be before the end.<br>• The start cannot be in the past.<br>• The reason has a maximum length of 300 characters.<br>• A maintenance block prevents overlapping bookings.<br>• A block cannot be created when it overlaps an existing active booking.<br>• A successful request returns `201 Created`.<br>• A nonexistent resource returns `404 Not Found`.<br>• A conflict with an existing booking returns `409 Conflict`.<br>• Invalid input returns `400 Bad Request`. | Todo |

# Module: Booking Reliability

| ID | User story | API | Acceptance criteria | Status |
|---|---|---|---|---|
| **US-014** | **As a user, I want confirmed bookings to be reliable, so that two users cannot reserve the same resource for overlapping periods.** | `POST /api/bookings` | • Two concurrent and overlapping booking requests for the same resource cannot both succeed.<br>• At most one request returns a successful response.<br>• The other request returns `409 Conflict`.<br>• The database contains at most one successful booking for the conflicting period.<br>• Concurrent non-overlapping bookings may both succeed.<br>• The behavior is covered by an integration test using PostgreSQL.<br>• Conflict protection must be transactionally or database-backed. | Todo |

# General Technical Requirements

These requirements apply across the project and are not separate user stories.

| Area | Requirement |
|---|---|
| Database | Database changes are managed through Flyway migrations. |
| API models | JPA entities are not used directly as public request or response contracts. |
| Validation | Client input is validated before the business operation is performed. |
| Transactions | Operations that change data use appropriate transaction boundaries. |
| Error handling | Expected client errors must not become `500 Internal Server Error` responses. |
| Security | Passwords, tokens, and production secrets are never committed to Git. |
| Testing | Important business rules are covered by automated tests. |
| Build | `.\mvnw.cmd clean verify` must succeed before a story is marked as done. |
